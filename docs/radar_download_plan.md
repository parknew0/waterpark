# 레이더 강수 데이터 추가 수집 계획

작성 2026-08-26. 다른 에이전트가 이 문서만 읽고 실행할 수 있도록 씀.

---

## 0. 한 줄 요약

**가장 중요한 변경은 "더 받는 것"이 아니라 "버리지 않는 것"이다.**
지금 수집기는 매 프레임 전국 격자 13.3MB를 내려받아 45,782개 지점만 뽑고 **나머지를
전부 버린다.** 격자를 저장하도록 고치면 **추가 다운로드 비용 0으로** 앞으로 어떤
지점이든 다시 뽑을 수 있다. 이걸 먼저 고치고 나서 받아야 한다.

## 2. 왜 더 받아야 하는가 — 세 가지 이유

### 이유 A. 채점 가능한 사건이 8개뿐이다

19개를 받았지만 실제 분석에 쓸 수 있는 건 8개다. 나머지는 침수점이 없거나
(대조 전용) 침수 시각을 모른다. 표본 8개로는:

- 강수량×지형 표의 많은 칸이 표본 부족으로 비어 있다 (예: 평지 150mm 이상)
- 사건 하나씩 빼는 교차검증에서 사건별 편차가 크다 (강수 AUC 0.45~0.99)
- "태풍은 전역을 적셔 강수 변별력이 없다"는 가설을 n=8에서 검증하지 못했다

**침수점이 있는데 아직 레이더를 안 받은 사건이 7개 남아 있다.**

| 사건 | 침수점 수 | 침수 시각 | 우선순위 |
|---|---|---|---|
| 20200728 | 2,003 | 08시 | **최우선** |
| 20230716 | 438 | **없음** | 보류 (아래 3-C 참고) |
| 20220810 | 256 | 10시 | 높음 |
| 20210706 | 84 | 05시 | 보통 |
| 20210824 | 54 | 12시 | 보통 |
| 20200810 | 47 | 16시 | 보통 |
| 20210711 | 39 | 19시 | 보통 |

6개(20230716 제외)를 받으면 채점 사건이 **8개 → 14개**로 늘어난다.

### 이유 B. 격자를 안 남겨서 분석이 두 번 막혔다

이번 분석에서 실제로 막힌 지점:

1. **대조군을 다시 뽑아야 했는데** 새 지점의 강수를 알 수 없었다. 결국 "가까운
   기존 지점의 비를 빌려 쓰는" 우회로를 썼다 (1km 이내면 오차 7%라 안전하긴 함).
2. **조사 범위를 2km 고리로 제한**해야 했다. 더 넓히면 빌려올 지점이 없다.

격자를 저장했다면 둘 다 문제가 아니었다. 앞으로도 계속 문제가 된다.

### 이유 C. 조사 범위 밖으로 확장하려면 격자가 필요하다

현재 침수 확률 표는 **침수 기록 2km 이내에서 센 값**이라 전국 비율이 아니다.
"침수 이력이 없는 지역도 예측"이라는 목표를 제대로 검증하려면 침수와 무관한
지역에서도 강수를 알아야 하고, 그건 격자가 있어야 한다.

## 3. 무엇을 어떻게 받는가

### 3-A. 먼저 코드를 고친다 (다운로드보다 우선)

`scripts/collect_radar_rainfall.py`에서 프레임을 디코드한 뒤 지점만 뽑고 격자를
버린다. **격자를 함께 저장하도록 바꾼다.**

- 원본: 2305×2881 int16 (13.3MB)
- 권장 저장: 원본 해상도 그대로 int16, `np.savez_compressed`
  - 비가 없는 칸이 대부분이라 압축이 잘 먹는다. 프레임당 2~5MB 예상
  - 사건당 39프레임 → **100~200MB**
- 대안(용량이 부담되면): 2×2 평균으로 1km로 줄여 저장 (프레임당 3.3MB → 1MB 내외).
  단 500m의 국지성이 목적이었으므로 **원본 해상도를 권장**한다.

저장 형식 제안: 사건별로 `rain_<YYYYMMDD>_grid.npz`를 따로 만든다
(기존 `rain_<YYYYMMDD>.npz`는 건드리지 말 것 — 지금 분석 코드가 그 형식을 읽는다).
키: `grid`(프레임×행×열 int16, dBZ×100), `stamps`, `span_min`, 격자 메타.

격자 규격 (이미 검증됨):
```
2305 x 2881, 500m, int16, 헤더 4바이트, 값 = dBZ x 100
-30000 = 레이더 범위 밖,  -25000 = 관측했으나 에코 없음
mm/h 변환: Z = 10^(dBZ/10);  R = (Z/200)^(1/1.6)   [Marshall-Palmer]
```

### 3-B. 1순위 — 빠진 6개 사건 (약 3.1GB)

```bash
# .env의 KMA_APIHUB_KEYS 사용
./.venv/bin/python scripts/collect_radar_rainfall.py \
  --events <6개_사건_json> \
  --points <scratchpad>/radar_points2.csv \
  --flood-hours <scratchpad>/event_hour.json \
  --hours-before 24 --step-min 10 --fine-hours 3 --coarse-step-min 60 \
  --workers 1 --min-interval 0.5 \
  --out data/interim/radar/events
```

사건 목록 JSON 내용:
```json
["20200728", "20220810", "20210706", "20210824", "20200810", "20210711"]
```

- 사건당 39프레임 × 13.3MB ≈ **519MB**
- 6개 = **약 3.1GB**

### 3-C. 20230716 문제

침수점 438개가 있는데 **침수 시각을 모른다.** 침수흔적 원본
(`data/raw/flood-trace/korea_flood_2002_2022.geojson`)이 2022년까지라 2023년
사건의 시각이 없다. 시각 없이 받으면 누적 창이 자정에서 끊겨 침수 이후의 비가
섞이고, 실제로 20220814·20230715가 이 문제로 분석에서 제외됐다.

**할 일 (다운로드 전):** 2023년 침수점의 출처(`wiseon`)에서 날짜·시각을 복구할 수
있는지 확인. 복구되면 20230715·20230716 둘 다 되살아난다 (침수점 3,448개).
복구 안 되면 이 사건은 받지 말 것 — 받아도 쓸 수 없다.

### 3-D. 2순위 — 기존 19개 사건 격자 재수집 (약 10GB)

다운로드 자체는 이미 하고 있던 것과 동일하다(같은 프레임을 같은 수만큼 받음).
**격자를 저장한다는 점만 다르다.** 기존 지점 데이터는 그대로 두고 격자 파일만
추가로 만든다.

- 19개 × 519MB ≈ **10GB**
- 하루 한도(키 3개 ≈ 15GB) 안에 들어간다

우선순위가 낮은 이유: 지금 있는 분석 결과는 지점 데이터만으로 이미 나왔다.
격자는 **앞으로의 확장**을 위한 것이다.

### 총량

| 단계 | 용량 | 비고 |
|---|---|---|
| 1순위: 빠진 6개 사건 | 3.1GB | 채점 사건 8 → 14 |
| 2순위: 기존 19개 격자 | 10GB | 확장성 확보 |
| 합계 | **약 13GB** | 키 3개 하루 한도 안 |

## 4. 반드시 지켜야 할 운영 규칙 (실패로 배운 것들)

### 4-1. 동시 접속 1개, 간격 0.5초

8워커로 4.4MB/s를 뽑다가 IP가 통째로 차단됐다. `--workers 1 --min-interval 0.5`가
검증된 안전 설정이다. 단일 연결로 **2.03MB/s, 프레임당 6.6초** 나온다.
사건 하나(39프레임)에 약 5분.

### 4-2. 차단 판별법

- `curl`의 `time_connect`가 **0.000s이고 HTTP 000** → IP 차단. 키 문제 아님.
  키를 바꿔도 소용없고 기다리는 수밖에 없다.
- **HTTP 403** → 그 키의 일일 한도 소진. 다음 키로 넘어가면 된다.
- 이 둘을 구분하지 못해 멀쩡한 키 3개를 몇 초 만에 폐기한 적이 있다.

### 4-3. `urlopen`의 timeout은 전체 시간이 아니다

소켓 연산 하나만 제한한다. 한도를 넘긴 IP에 서버가 바이트를 조금씩 흘리면 매
`read`가 타임아웃에 안 걸려 **7초짜리 프레임이 20분** 걸린다. 청크로 읽으며
벽시계 마감(45초)을 따로 둘 것. 이미 반영돼 있으니 지우지 말 것.

### 4-4. `pkill -f collect_radar_rainfall` 금지

진단 스크립트의 명령줄에도 그 문자열이 들어가서 **스크립트가 자기 자신을 죽인다.**
출력이 텅 빈 채 끝나면 이걸 의심할 것. PID로 종료하라.

### 4-5. 진행 표시는 시간 기준으로

"24프레임마다"로 찍으면 1워커에서 30분간 무음이라 멈춘 것과 구별이 안 된다.
이것 때문에 멀쩡히 돌던 작업을 여러 번 죽였다.

### 4-6. 불완전한 파일을 저장하지 말 것

프레임의 90% 미만만 받았으면 저장하지 않는다(이미 구현됨). 저장해버리면 다음
실행에서 "완료"로 보고 건너뛴다. 실제로 0/288짜리 스텁 6개가 생겼었다.

### 4-7. 키 순환

`KeyRing`이 403/401/429일 때만 키를 폐기하고, 연결 실패는 폐기하지 않는다.
이 구분이 핵심이다.

## 5. 받은 뒤 실행할 것

```bash

  --points <radar_points2.csv> --anchor-hours <event_hour.json> \
  --out data/processed/ml/training/ring_census.csv

./.venv/bin/python scripts/build_rain_threshold_table.py \
  --out outputs/flooded-building-register/rain_threshold_table.json

# 4) 지형 대비 강수 기여도 검증
./.venv/bin/python scripts/eval_rain_terrain.py --exclude-events 20220814,20230715

./.venv/bin/python scripts/eval_rain_falsification.py   # 반증 시험
```

`--exclude-events`는 침수 시각을 모르는 사건 목록이다. 20230716을 시각 없이
받았다면 여기에 추가해야 한다.

## 6. 하지 말아야 할 것

- **관측소(AWS) 강수로 대체하지 말 것.** 강수를 돌려주는 지점은 658곳뿐이고
  이웃까지 중앙 8.1km다. 비가 오는 곳에서 이웃 관측소와 1시간 강수가 중앙 9.2mm,
  세게 오는 곳에선 17.0mm(자기 값의 41%) 차이 난다. 레이더 500m의 이유가 이것이다.
- **해상도를 낮춰 받지 말 것.** 다운로드 용량은 어차피 같다(서버가 500m로 준다).
  줄이는 건 저장할 때만 의미가 있고, 그러면 되돌릴 수 없다.
- **`depth_cm`을 침수 깊이로 쓰지 말 것.** 비와 무관(−0.037)하고 높은 곳·가파른
  곳일수록 깊다고 나온다(+0.292, +0.151). 지표면 침수심이 아니다.

## 7. 갱신 2026-08-27 저녁 — 대용량 API 승인 이후

기상청이 대용량 API를 승인하면서 위 계획의 전제가 바뀌었다.

| | 기존 키 3개 | 대용량 키 |
|---|---|---|
| 일 한도 | 5GB x 3 | **2TB** |
| 호스트 | apihub.kma.go.kr | **apihub-org.kma.go.kr** |
| 실측 속도 | 0.2~2 MB/s | **4.5~5.3 MB/s** (16병렬) |
| 사용시간 | 제한 없음 | **15:00~24:00**, 2026-08-28~09-04 |

키는 `.env`의 `KMA_APIHUB_ORG_KEY` / `KMA_APIHUB_ORG_HOST`에 있다. 수집기는
`KMA_APIHUB_HOST` 환경변수로 호스트를 바꾼다.

**병렬은 16이 천장이다.** 16개는 전부 성공, 32개는 즉시 전부 거부된다.

### 새 자료가 다 모인 뒤 할 일

1. 131개 전부에 대해 침수 시각 검증 — 침수점 위 6시간 강수가 최대가 되는 마감 시각을

2. `--radar-dir data/interim/radar/events_full`로 5절의 명령들을 다시 실행.
3. 결과가 기존보다 나으면 `events/`를 대체한다.
